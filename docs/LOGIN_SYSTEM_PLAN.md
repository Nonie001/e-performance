# แผนพัฒนาระบบ E-Performance: Phase 1 — Login

เอกสารนี้ใช้เป็นแผนเริ่มต้นสำหรับระบบประเมินผลการปฏิบัติงานพนักงาน โดย Phase 1 จะเริ่มจากการออกแบบและพัฒนาหน้า Login ให้เสร็จก่อน แล้วจึงเชื่อมต่อข้อมูลพนักงานและแบบประเมินในลำดับถัดไป

## 1. เป้าหมายของระบบโดยรวม

ระบบ E-Performance เป็น Web Application สำหรับให้พนักงานประเมินตนเอง และให้หัวหน้างานติดตามสถานะ ดูคะแนนของลูกน้อง และประเมินลูกน้องตามลำดับการอนุมัติของบริษัท

ข้อมูลหลักของระบบจะมาจากฝ่าย HR และใช้ Google Sheets เป็นฐานข้อมูลในระยะแรก

## 2. ขอบเขต Phase 1

Phase 1 เน้นระบบเข้าสู่ระบบและการเตรียมโครงสร้างสำหรับหน้าถัดไป ประกอบด้วย:

1. ออกแบบหน้า Login ให้ใช้งานได้ทั้งคอมพิวเตอร์และโทรศัพท์มือถือ
2. ใช้รหัสพนักงานเป็น Username
3. กำหนดรหัสผ่านเริ่มต้นสำหรับการเข้าใช้งานครั้งแรก
4. บังคับเปลี่ยนรหัสผ่านหลัง Login ครั้งแรก
5. แสดงข้อความแจ้งเตือนเมื่อกรอกข้อมูลไม่ถูกต้อง
6. เตรียมการแยกสิทธิ์ผู้ใช้งาน เช่น พนักงาน หัวหน้างาน GM และ HR/Admin
7. เตรียมเส้นทางไปยัง Dashboard หลังเข้าสู่ระบบสำเร็จ

สิ่งที่ยังไม่รวมในการทำหน้า Login รอบแรก:

- แบบประเมินตนเอง 20–30 รูปแบบ
- Dashboard รายชื่อลูกน้องฉบับสมบูรณ์
- การให้คะแนนโดยหัวหน้างาน
- Workflow ส่งต่อหัวหน้าฝ่ายหรือ GM
- รายงานสรุปผลสำหรับ HR

## 3. แนวทางหน้าตา Login

### 3.1 ภาพลักษณ์

- ใช้โลโก้ Innovation Technology เป็นองค์ประกอบหลักด้านบนของกล่อง Login
- ไฟล์โลโก้ในโปรเจกต์: `/public/innovation-technology-logo.webp`
- โทนสีหลักอ้างอิงจากโลโก้:
  - สีน้ำเงินเข้ม ใช้กับหัวข้อ ปุ่มหลัก และจุดเน้น
  - สีขาว ใช้เป็นพื้นหลังของกล่อง Login
  - สีเทาอ่อน ใช้เป็นพื้นหลังหน้าเว็บและเส้นขอบ
- รูปแบบควรดูเป็นระบบงานภายในองค์กร: สะอาด สุภาพ อ่านง่าย และไม่ซับซ้อน

### 3.2 องค์ประกอบบนหน้าจอ

หน้า Login ควรมี:

- โลโก้บริษัท
- ชื่อระบบ `E-Performance`
- คำอธิบาย `ระบบประเมินผลการปฏิบัติงาน`
- ช่อง `รหัสพนักงาน`
- ช่อง `รหัสผ่าน`
- ปุ่มแสดง/ซ่อนรหัสผ่าน
- ปุ่ม `เข้าสู่ระบบ`
- พื้นที่แสดงข้อความผิดพลาด
- ข้อความช่วยเหลือสำหรับผู้ที่ไม่สามารถเข้าสู่ระบบได้ เช่น ให้ติดต่อฝ่าย HR
- ปีลิขสิทธิ์และชื่อบริษัทบริเวณด้านล่าง

บนหน้าจอคอมพิวเตอร์ กล่อง Login จะอยู่กึ่งกลางหน้าและมีพื้นที่ว่างรอบด้าน ส่วนบนโทรศัพท์มือถือ กล่องจะขยายเกือบเต็มความกว้างโดยยังมีระยะขอบที่กดใช้งานได้สะดวก

## 4. ขั้นตอนการใช้งาน

### 4.1 การเข้าใช้งานครั้งแรก

```text
เปิดหน้า Login
→ กรอกรหัสพนักงานและรหัสผ่านเริ่มต้น
→ ระบบตรวจสอบข้อมูล
→ ระบบพบว่ายังไม่เคยเปลี่ยนรหัสผ่าน
→ ไปหน้าเปลี่ยนรหัสผ่าน
→ ตั้งรหัสผ่านใหม่สำเร็จ
→ ไปยัง Dashboard ตามสิทธิ์ของผู้ใช้
```

### 4.2 การเข้าใช้งานครั้งถัดไป

```text
เปิดหน้า Login
→ กรอกรหัสพนักงานและรหัสผ่านใหม่
→ ระบบตรวจสอบข้อมูลและสิทธิ์
→ ไปยัง Dashboard ตามบทบาท
```

### 4.3 กรณีเข้าสู่ระบบไม่สำเร็จ

- ไม่พบรหัสพนักงาน: แสดงข้อความ `ไม่พบข้อมูลผู้ใช้งาน กรุณาตรวจสอบรหัสพนักงาน`
- รหัสผ่านไม่ถูกต้อง: แสดงข้อความ `รหัสพนักงานหรือรหัสผ่านไม่ถูกต้อง`
- บัญชีถูกระงับ: แสดงข้อความให้ติดต่อ HR
- ระบบเชื่อมต่อข้อมูลไม่ได้: แสดงข้อความทั่วไปและให้ลองใหม่ โดยไม่แสดงรายละเอียดทางเทคนิค

## 5. บทบาทผู้ใช้งานที่ต้องรองรับ

| บทบาท | สิทธิ์หลัง Login |
|---|---|
| Employee | ดูข้อมูลตนเองและทำแบบประเมินตนเอง |
| Supervisor / Manager | ดูข้อมูลตนเอง ดูรายชื่อลูกน้อง และประเมินลูกน้อง |
| Department Head | ตรวจสอบหรือประเมินรายการที่ส่งมาจากฝ่ายตาม Workflow |
| GM | ตรวจสอบและประเมินรายการที่ส่งถึง GM |
| HR / Admin | จัดการข้อมูลพนักงาน แบบประเมิน รอบประเมิน และดูภาพรวม |

ผู้ใช้หนึ่งคนอาจมีมากกว่าหนึ่งบทบาท เช่น เป็นทั้งพนักงานและหัวหน้างาน ระบบจึงควรเก็บบทบาทแยกจากข้อมูลบัญชีผู้ใช้

## 6. ข้อมูลที่ต้องเตรียมจาก HR

อย่างน้อยต้องมีข้อมูลต่อไปนี้:

| ข้อมูล | ตัวอย่างการใช้งาน |
|---|---|
| รหัสพนักงาน | ใช้เป็น Username |
| คำนำหน้า ชื่อ และนามสกุล | แสดงตัวตนหลัง Login |
| อีเมลหรือช่องทางติดต่อ | ใช้สำหรับแจ้งเตือนหรือกู้บัญชีในอนาคต |
| ตำแหน่ง | เลือกแบบประเมินให้ตรงกับงาน |
| แผนก/ฝ่าย | กำหนด Workflow |
| รหัสหัวหน้างาน | เชื่อมความสัมพันธ์หัวหน้า–ลูกน้อง |
| บทบาทในระบบ | กำหนดสิทธิ์การเข้าถึง |
| สถานะพนักงาน | อนุญาตหรือระงับการเข้าสู่ระบบ |
| สถานะการเปลี่ยนรหัสผ่าน | ตรวจสอบว่าต้องบังคับเปลี่ยนรหัสผ่านหรือไม่ |

## 7. แนวทางด้านรหัสผ่านและความปลอดภัย

ข้อกำหนดเดิมระบุให้ใช้เลขบัตรประชาชนเป็นรหัสผ่านเริ่มต้น แต่เลขบัตรประชาชนเป็นข้อมูลส่วนบุคคลที่มีความอ่อนไหว จึงควรใช้เฉพาะในขั้นตอนเริ่มต้นหากจำเป็น และต้องบังคับเปลี่ยนทันทีหลังเข้าใช้งานครั้งแรก

แนวทางที่แนะนำ:

- ไม่เก็บรหัสผ่านหรือเลขบัตรประชาชนเป็นข้อความปกติใน Google Sheets
- เก็บรหัสผ่านในรูปแบบที่ผ่านการ hash เท่านั้น
- จำกัดจำนวนครั้งที่ Login ผิดติดต่อกัน
- บันทึกวันเวลาและผู้ใช้งานที่เข้าสู่ระบบ โดยไม่บันทึกรหัสผ่าน
- ไม่ส่งรหัสผ่านกลับไปยังหน้าเว็บหรือแสดงใน log
- ใช้ HTTPS ในระบบจริง
- กำหนด Session หมดอายุ และมีปุ่มออกจากระบบ
- พิจารณาใช้รหัสเริ่มต้นแบบชั่วคราวแทนเลขบัตรประชาชน เพื่อลดความเสี่ยง

> หมายเหตุ: Google Sheets เหมาะสำหรับข้อมูล Master และข้อมูลประเมินในระยะแรก แต่ไม่ควรให้ Browser อ่านหรือเขียน Sheet โดยตรง ควรติดต่อผ่าน Server/API ที่ตรวจสอบสิทธิ์ทุกครั้ง

## 8. หน้าจอที่เกี่ยวข้องกับ Phase 1

### 8.1 หน้า Login

- Route ที่เสนอ: `/login`
- ผู้ใช้ที่ยังไม่ Login และเปิดหน้าอื่น จะถูกส่งกลับมาหน้านี้
- ตรวจสอบช่องว่างและรูปแบบข้อมูลก่อนส่งคำขอ
- ระหว่างตรวจสอบให้ปิดปุ่มชั่วคราวและแสดงสถานะกำลังเข้าสู่ระบบ

### 8.2 หน้าเปลี่ยนรหัสผ่านครั้งแรก

- Route ที่เสนอ: `/change-password`
- ช่องรหัสผ่านใหม่
- ช่องยืนยันรหัสผ่านใหม่
- แสดงเงื่อนไขของรหัสผ่านอย่างชัดเจน
- ไม่อนุญาตให้ข้ามหน้าไป Dashboard ก่อนเปลี่ยนสำเร็จ

### 8.3 หน้า Dashboard ชั่วคราว

- Route ที่เสนอ: `/dashboard`
- แสดงชื่อ รหัสพนักงาน ตำแหน่ง และบทบาท
- ใช้เป็นหน้าปลายทางเพื่อยืนยันว่า Login และการเปลี่ยนรหัสผ่านทำงานครบวงจร
- ฟังก์ชันประเมินตนเองและ Dashboard หัวหน้างานจะพัฒนาใน Phase ถัดไป

## 9. สถานะของหน้า Login

หน้าจอต้องรองรับสถานะต่อไปนี้:

1. Default — พร้อมให้กรอกข้อมูล
2. Validation Error — กรอกข้อมูลไม่ครบ
3. Loading — กำลังตรวจสอบข้อมูล
4. Authentication Error — รหัสพนักงานหรือรหัสผ่านไม่ถูกต้อง
5. Account Disabled — บัญชีไม่สามารถใช้งานได้
6. Connection Error — ติดต่อระบบไม่ได้
7. Success — เข้าสู่ระบบสำเร็จและกำลังเปลี่ยนหน้า

## 10. Acceptance Criteria ของหน้า Login

ถือว่าหน้า Login รอบแรกเสร็จเมื่อ:

- แสดงโลโก้ Innovation Technology ได้คมชัดและไม่บิดเบี้ยว
- ใช้งานได้ตั้งแต่หน้าจอมือถือขนาดเล็กจนถึงคอมพิวเตอร์
- กรอกและตรวจสอบรหัสพนักงานกับรหัสผ่านได้
- กด Enter เพื่อเข้าสู่ระบบได้
- แสดง/ซ่อนรหัสผ่านได้
- มี Loading state และป้องกันการกดซ้ำ
- แสดงข้อความผิดพลาดที่เข้าใจง่าย
- ผู้ใช้ครั้งแรกถูกส่งไปหน้าเปลี่ยนรหัสผ่าน
- ผู้ใช้ที่เปลี่ยนรหัสผ่านแล้วถูกส่งไป Dashboard
- ผู้ใช้ที่ยังไม่ Login ไม่สามารถเปิดหน้าภายในระบบโดยตรงได้
- ไม่มีรหัสผ่าน เลขบัตรประชาชน หรือข้อมูลลับปรากฏใน log ฝั่ง Browser
- ผ่านการตรวจสอบบน Chrome และ Microsoft Edge เวอร์ชันที่บริษัทใช้งาน

## 11. ลำดับการพัฒนา

### รอบที่ 1: หน้าตาและประสบการณ์ใช้งาน

- นำโลโก้มาใช้ในหน้า Login
- จัดทำ Responsive layout
- ทำช่องกรอก ปุ่ม และสถานะต่าง ๆ
- ใช้ข้อมูลจำลองเพื่อทดสอบเส้นทาง Login

### รอบที่ 2: ระบบยืนยันตัวตน

- กำหนดรูปแบบข้อมูลพนักงานจาก HR
- สร้าง Server/API สำหรับตรวจสอบบัญชี
- ทำระบบ Session และการออกจากระบบ
- ทำหน้าเปลี่ยนรหัสผ่านครั้งแรก
- เชื่อมสิทธิ์กับบทบาทผู้ใช้งาน

### รอบที่ 3: เชื่อม Google Sheets

- กำหนด Sheet และชื่อคอลัมน์มาตรฐาน
- เชื่อมผ่าน Google Apps Script Web App โดยให้ Next.js Server เป็นผู้เรียกใช้งาน
- เพิ่มการตรวจสอบสิทธิ์ก่อนอ่านหรือบันทึกข้อมูล
- จัดการกรณี Sheet ช้า ใช้งานไม่ได้ หรือข้อมูลไม่ครบ

## 12. ประเด็นที่ต้องยืนยันก่อนเชื่อมระบบจริง

1. บริษัทอนุญาตให้ใช้เลขบัตรประชาชนเป็นรหัสผ่านเริ่มต้นหรือไม่
2. Google Apps Script เป็นตัวกลางสำหรับอ่านและเขียนแท็บ `UserCredentials`
3. ใครเป็นผู้ดูแลการเพิ่ม ปิด และแก้ไขบัญชีพนักงาน
4. เงื่อนไขรหัสผ่านใหม่ เช่น ความยาวขั้นต่ำ ตัวเลข และตัวอักษร
5. ต้องมีระบบลืมรหัสผ่านใน Phase 1 หรือให้ HR เป็นผู้รีเซ็ต
6. Session ต้องหมดอายุภายในกี่นาทีหรือกี่ชั่วโมง
7. ชื่อบริษัทและข้อความลิขสิทธิ์ที่ต้องแสดงอย่างเป็นทางการ
8. รายชื่อบทบาทและสิทธิ์ที่ HR ยืนยันแล้ว

## 13. งานลำดับถัดไป

หลังอนุมัติแผนนี้ ให้เริ่มพัฒนาหน้า Login ตาม Wireframe โดยใช้โลโก้ที่เตรียมไว้ จากนั้นจึงทำหน้าเปลี่ยนรหัสผ่านและ Dashboard ชั่วคราวเพื่อทดสอบ Flow ให้ครบก่อนเชื่อม Google Sheets จริง
